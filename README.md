# Youth baseball club website

Django scaffold reflecting the planning decisions in
`baseball_club_website_plan.md`. This was hand-written (not generated by
`django-admin startproject`) since the environment that built it had no
network access -- verify everything against a real `django-admin` project
once you have Django installed locally, and treat this as a strong
starting skeleton rather than a finished, tested app.

## Local setup 


```bash
brew install postgresql@16
brew services start postgresql@16
createdb baseball_club
```

Then, in the project root:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# edit .env: set SECRET_KEY to a real random string

python manage.py migrate
python manage.py createsuperuser

my 201email.

python manage.py runserver
```

Visit `http://127.0.0.1:8000/admin/` to confirm the models show up in the
Django admin.

## Project layout

```
config/          # settings, root urls, wsgi entrypoint
apps/
  accounts/      # custom User, many-to-many roles, Player, parent-player
                 # linking, second-parent invites
  teams/         # Team, TeamCoach (head/assistant, coach can be on
                 # multiple teams), CoachProfile (bio), PlayerPosition
  tryouts/       # TryoutSignup, year auto-tagging with admin-editable
                 # cutoff, status + confirmation audit trail
  schedule/      # single Event model for practices + tournaments
  fees/          # ledger-style Fee + Payment (no in-house payment
                 # processing -- add Stripe/Square later if needed)
templates/       # Django templates (empty scaffold -- pages not yet built)
static/          # your own CSS/JS/images (served via WhiteNoise)
```

## What's deliberately not built yet

- No views/templates -- only models, admin registrations, and empty
  urls.py files per app. Views are the next step.
- No HTMX-specific endpoints yet (status-change dropdown + confirmation,
  payment recording, invite-link flow) -- `django-htmx` is installed and
  wired into settings, ready to use.
- No permission/decorator layer enforcing the role rules yet (e.g. "coach
  can edit own team's roster, view-only on tournaments, never sees fees
  unless they also hold the Admin role"). `User.has_role()` /
  `User.is_admin` / `.is_coach` / `.is_parent` on the custom User model
  are the building blocks for that layer.
- No GameChanger ICS sync -- pending confirming a subscribable feed URL
  exists (see the plan doc).

## Deploying to Railway

1. Push this repo to GitHub.
2. Create a Railway project, add a Postgres addon -- it injects
   `DATABASE_URL` automatically, matching what `config/settings.py`
   expects.
3. Set `SECRET_KEY`, `DEBUG=False`, and `ALLOWED_HOSTS` as Railway
   environment variables.
4. Set `USE_R2=True` plus the `R2_*` variables once the Cloudflare R2
   bucket is created, for coach-photo and future media uploads.
5. Railway runs `release: python manage.py migrate` automatically before
   each deploy (see `Procfile`), then starts the app via gunicorn.
